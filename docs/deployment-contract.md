### Request validity, errors and compatibility

The accepted semantic rule maps Pipeline's required `validUntil` to **the earlier of the trusted bounded request deadline and the validated Entra actor-token expiry**. Require completion before that bound; an expired/exhausted bound cannot yield reusable facts. This is request validity, not a promise that GitHub permissions stay unchanged until that time. The core currently exposes `observedAt` only; the adapter must not invent a provider TTL to fill Pipeline's local port.

Continue fresh provider reads on each protected request, without positive caching between requests. Reuse within one request requires the exact same binding and current generation. Re-read the link at the end of multiple calls; changed/lost generation fails closed, including disconnect/relink at the same source timestamp. Preserve fixed outcomes: connection/reconnection required for lost linkage or definitive user authorization loss; denied for an ineligible authenticated selection; unavailable for outages, rate limits, malformed/incompatible facts or uncertain dependencies. Do not expose provider error bodies, exception causes or secrets. Resource absence/denial must not reveal unrelated resources. Transport status/error fields remain pending.

Before integration, agree deadline origin/propagation, clock skew and accepted observation bounds, batch/page/response limits, cancellation, safe-read retry and GitHub quota budgets. No numeric values are inferred here. Unknown operations, incompatible versions or changed binding/permission semantics fail closed. Agree version negotiation and compatibility windows before connecting consumers; parseable JSON alone does not establish semantic compatibility.

### Locally accepted Key Vault Secrets protocol

Assume modest MVP load and an encoded credential pair smaller than Key Vault's 25 KB secret limit; **neither workload nor latency/quota assumptions have been measured**. Use one secret object per connection generation, with each new version containing the access token, refresh token and provider-supplied expiries together as one value. This keeps each pair in one atomic Key Vault version; it does not create atomicity with metadata or GitHub. [Key Vault secrets](https://learn.microsoft.com/en-us/azure/key-vault/secrets/about-secrets) are opaque stored values; the application owns pair semantics and expiry enforcement.

The accepted physical linkage, generation, OAuth-attempt and durable credential-operation definitions live in [Docs domain decisions](https://github.com/pipesor-org/pipesor-docs/blob/main/model/domain_decisions.md), including exact-version references, ownership checks and local atomicity. Key Vault holds credentials and the proposed temporary PKCE verifier; PostgreSQL metadata contains no plaintext verifier, access/refresh token, authorization code or raw provider error. Resolve references only within the approved vault and the generation/attempt-owned object with its exact version; never accept a client-supplied vault URL, object path or version as authority. Never resolve `latest` for an active generation. Secret values, names, tags and references must not leak into client results or technical/audit diagnostics. Names and operation markers must not contain tokens or identity/profile material. The physical schema and Secrets usage are accepted locally; this does not implement the actual Key Vault adapter or supply runtime access/recovery policy.

An [envelope-encryption design](https://learn.microsoft.com/en-us/azure/storage/blobs/client-side-encryption#encryption-and-decryption-via-the-envelope-technique), with keys in Key Vault and ciphertext in an approved owned store, remains an alternative if measured scale, latency or recovery requirements justify its cryptography and operations. The linked technique does not authorize Blob or its SDK. Do not select that alternative or reopen the approved Key Vault product choice without relevant evidence.

Key Vault `exp` does not block secret retrieval; enforce GitHub expiries, revocation and generation validity in the application. [Soft-delete and purge protection](https://learn.microsoft.com/en-us/azure/key-vault/general/soft-delete-overview) retain recoverable material and can delay purge. Deactivating a metadata reference is not physical deletion or removal of an individual old version. Define backup/recovery/deletion obligations separately from local disconnection; the 365-day evidence policy is not credential retention.

### Connection, refresh and disconnect recovery

For connection, require unpredictable, expiring, single-use state bound to the authenticated Entra attempt, approved redirects and PKCE `S256`. Durably claim/consume the callback once before exchanging the code; verify the actual GitHub user, save the credential pair and conditionally activate the intended generation. An expired/replayed/mismatched callback fails without including code, state or verifier in errors/logs. [GitHub's user-token flow](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app) supports state and PKCE; the durable-claim/recovery rules here are part of the locally accepted design. No blind callback/code-exchange retry after an uncertain outcome. The PKCE verifier is itself secret: the accepted design uses temporary Key Vault custody, referenced by the durable attempt and cleaned up separately. Preparing that secret and recording the attempt is not a distributed transaction; do not publish authorization navigation until the referenced material and a usable attempt are both confirmed.

**Browser/return-channel decision remains open:** specify how callback completion proves binding to the initiating browser/session or requires authenticated confirmation, accounting for the dashboard/service origins and ingress. Do not assume a cookie works across the SPA's origins, infer a new BFF/gateway, or treat code/state/installation IDs as an Entra login. State recovers the server-bound attempt; PKCE and the accepted return/session protocol must close the callback threat model before an adapter is implemented. The PD-035 handoff must also prevent authorization codes, raw state and tokens from entering ingress/access logs, trace URLs, error reports or return URLs; application-level redaction alone does not establish that exposure is safe.

Accepted metadata phases: **durable exclusive claim for the exact generation/revision → GitHub refresh → write exact Key Vault version → guarded metadata activation using compare-and-set/fencing**. The claim survives process crashes and excludes concurrent refresh; no SQL transaction/lock is held over network calls. Local database exclusion follows accepted DD-020 and is checked independently from remote custody execution; the actual recovery executor and operating inputs remain pending. There is no distributed transaction across GitHub, Key Vault and metadata.

[GitHub refresh invalidates both the used refresh token and its old access token](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/refreshing-user-access-tokens). A lost response can therefore lose the only usable pair. Lease expiry does not prove that retrying GitHub is safe; fencing protects metadata activation, not GitHub's remote side effect. Never retry the old pair or roll back to it after an uncertain refresh.

| Failure phase | Accepted required behavior |
|---|---|
| Before a refresh request was sent, with durable evidence | Return unavailable; recovery may safely release/reclaim the operation. Do not confuse this with an uncertain send. |
| Request may have reached GitHub, but no usable returned pair is durably recoverable | Block credential use/refresh and require reconnection; do not retry the old pair after a timeout or lease expiry. |
| New pair received, but Key Vault save is uncertain or failed | Return unavailable; recover only with durable evidence tying a usable exact version to that operation. Otherwise block/reconnect; never fall back to the invalidated pair. |
| Exact Key Vault version saved, metadata activation failed | Reconcile only that version/operation under the unchanged generation and fencing guard, using durable evidence. Never read `latest` or activate an unproven candidate; absent sufficient evidence, block/reconnect. |
| Disconnect/relink wins while callback/refresh is in flight | Reject late activation by generation/revision comparison. Record cleanup/revocation for late or superseded material; never resurrect the old link. |
| Definitive revocation/invalid refresh credentials | Require reconnection; distinguish from a transient dependency outage. |

Disconnect first durably invalidates the local generation and records cleanup/upstream-revocation intent in the same local atomic decision; then perform external cleanup. Report local disconnected status separately from confirmed upstream revocation and eventual Key Vault deletion/purge. Persist progress/failures for recovery and sanitized audit, not credentials. If cleanup cannot complete, the invalid generation must remain unusable.

Distinguish local invalidation, upstream revocation, Key Vault deletion, purge and backup removal/recovery. Scope cleanup intent to the target generation's credentials; the exact GitHub revocation operation and blast radius still require approval. Do not infer App-wide user-authorization revocation or affect other links for the same GitHub user: reverse uniqueness is not approved, and any broader revocation requires explicit impact acceptance. Define cleanup of superseded versions and per-generation objects without claiming immediate erasure. Relink creates a new generation; late work cannot activate either prior or unclaimed credential material. Disconnect changes no shared machine-monitoring decision, Pipeline grants, ACTIVE/PAUSED status or data retention by inference. Installation loss and already captured/in-flight evidence remain subject to ADR-020 and PD-033.

**Accepted restore requirement; operating mechanism pending:** a metadata restore must not silently restore authorization. Before restored data can serve protected requests, the accepted PD-035 recovery procedure must keep the service unavailable and reconcile against authoritative post-backup invalidations/cleanup state. Fresh GitHub checks alone do not prove that an AIOps connection was not disconnected after the backup. If that authoritative state cannot be recovered, invalidate restored generations and require new user connection under the agreed recovery protocol. The requirement is approved; it does not implement a restore detector, approve an external journal or create a resource.

**Current conservative recovery limit:** the metadata implementation preserves an exact late acknowledgement even after a refresh is `BLOCKED` and the connection has been relinked. That acknowledgement does not reactivate the old generation or resolve the refresh. While any refresh remains nonterminal, even confirmed cleanup results and a trusted no-late-write signal leave final cleanup `BLOCKED`. A terminal reconciliation protocol for an obsolete/uncertain refresh must be specified before a real recovery executor can certify cleanup; no automatic retry, final erasure or complete operational lifecycle is claimed by this increment.

## Durable capture/publication lifecycle

The user subsequently directed “Vamos a por ello” after the concrete four-table persistence proposal and implementation plan. Three logical kinds of owned record are represented by four tables; delivery aliases have their own receipt-membership relation:

| Record | Contents and ownership |
|---|---|
| Authenticated capture receipt | Owner-generated UUID; trusted capture-domain/tenant binding; source and verified App/account/installation/repository/workflow/run/attempt; admitted-scope revision; delivery ID; private SHA-256 of the authenticated body; content-bound receipt key; original correlation; acceptance time, phase/revision and fixed failure reason. | Prepared observation | Receipt association; stable source-observation key, actual observed upstream version/timestamps; version of normalization/protection policy; private canonical digest of protected content; immutable output plan. | Publication output | Message UUID allocated once; type/major and source fragment locator where applicable; exact protected JSON bytes/digest and coherent broker identity/correlation/routing; phase/revision, claim fence/lease, attempt count/time, broker-confirmation time and fixed failure reason. Receipt identity and observation identity have different purposes. The persisted receipt tuple is `(trusted capture domain, source, authenticated-body SHA-256)`; no second opaque receipt hash is required. Delivery ID is auxiliary: identical authenticated content under a changed delivery header recovers the same receipt; reuse of one delivery ID with conflicting content is an integrity failure. Full tenant/App/account/installation/repository/workflow/run/attempt binding is checked independently. Excluding the mutable scope revision from dedup identity cannot turn it into permission: the mandatory scope port checks the current exact revision before preparation/publication. Neither digest nor receipt identity authorizes a read or is published as evidence identity.

The prepared observation binds external repository/workflow/run/attempt, actual upstream source version and canonical protected content, plus a source job/step/fragment locator for evidence. The implemented v1 encoding uses JDK UTF-8 fields with int32 big-endian byte lengths, an explicit null marker, canonical list order and source epoch-second/nanosecond values. It excludes random IDs, correlation, mutable scope revision, policy deployment versions and technical clocks. It includes both original source timestamps and protected execution/stage/failure/evidence contents. Equal upstream timestamps with different content remain different keys, preserving Pipeline's conflict policy; normalization does not choose a winner. The locator is explicit canonical `v1:job:<positiveDecimal>:step:<positiveInt>:index:<nonnegativeInt>`. It identifies the selected excerpt without inferring job classification or complete log coverage. Real extraction/authorization remains the future source adapter's responsibility. Public evidence UUIDs retain their approved rule.

Implemented receipt phases: `ACCEPTED → PREPARED → PUBLISHED`, with `BLOCKED` preserving work requiring recovery. Output phases: `PENDING → CLAIMED → CONFIRMED`, with `BLOCKED` preserving permanent failures. A claim expires without proving the broker did not accept a send: retry the original immutable message ID/body/properties. Unlike an uncertain GitHub token refresh, a stable broker publication is designed for at-least-once retry. Only the current fenced claimant may confirm/update an output; a stale acknowledgement cannot overwrite a later claim's state. An operational unblock/reconciliation procedure is not supplied by this increment.

The acceptance transaction stores the minimum recoverable receipt and two reserved UUIDs before the internal API returns. No public webhook is present to map that result to a source acknowledgement yet. Preparation freezes the observation and complete one/two-output plan in a transaction before sending. A failed attempt waits for its classified protected excerpt; extraction/protection failure leaves no partially sendable plan. No SQL transaction spans a GitHub, scope-provider or broker call. Two broker sends still have no distributed atomicity: individual confirmations and stable retries track their different outcomes.

A receipt is published only when every required output is broker-confirmed. Confirmation means broker acceptance, not that Pipeline, Log/Event and NLP have all committed. Retry only unconfirmed outputs, retaining identity/body; a lost acknowledgement can legitimately result in duplicate delivery. Already frozen outputs are not regenerated after a new GitHub read, policy version change or process restart. Revalidate current machine scope before protected reads/publication; personal unlink still does not by itself terminate shared machine monitoring. Revocation treatment for already accepted/in-flight work remains the explicit cutoff input, not an inferred delete/drop operation.

Recommend independent retention horizons: remove confirmed protected bodies after the publication/recovery horizon, and retain minimized receipt identity/digests for the authorized replay horizon. No duration is selected here and the 365-day evidence rule is not a default for this technical buffer. Pending/blocked work cannot be purged silently to free capacity: apply backpressure and operator recovery. Protection against a replay after receipt deletion cannot be promised. Capacity, authorized historical recovery and cleanup must be agreed with those horizons before activation.
