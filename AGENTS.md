# Repository instructions

## Context by task

- Before implementation, read the [common backend conventions](https://github.com/pipesor-org/pipesor-docs/blob/main/docs/development/backend-conventions.md) and [Java/Spring conventions](https://github.com/pipesor-org/pipesor-docs/blob/main/docs/development/java-spring-conventions.md). Use the accessible pipesor-docs checkout when available, distinguishing local changes from integrated main. Apply only the conventions relevant to this service; they do not add tables, integrations or permissions.
- Use [README.md](README.md#development-and-verification) for setup, runnable commands and contribution policies. Add verified commands there when introducing application tooling; reference them rather than maintaining a second command list here.
- For capture, normalization, privacy or publication changes, consult [architecture](docs/architecture.md#service-relationships) and its current source model, including this service's canonical event context. For GitHub authentication changes, consult ADR-005 and the [approved ADR-020 evolution](docs/architecture.md#approved-github-access-evolution), distinguishing its local source overlay from integrated main. Follow the references for the affected subject, not the entire documentation set for every edit.
- For dependency selection, runtime configuration, credentials or delivery work, consult the relevant sections of the [deployment contract](docs/deployment-contract.md). Its development baseline records the authorized version-selection policy; the data lifecycle distinguishes the historical absence of owned tables from ADR-020 logical connector ownership with physical schema/custody still pending.
- Treat local architecture summaries as navigation, not frozen specifications. Use the accessible `../../pipesor-docs/` checkout or linked sources on `main`, accounting for later accepted decisions and relevant uncommitted changes. Inspect uncommitted source changes separately; their presence does not establish integration or approval. Report unavailable or conflicting evidence when it affects the task. Documentation links must follow `main` across repositories and relative paths within this repository; a consulted revision may be recorded as text only.

## Implementation constraints

- Keep machine capture within the authorized repository/workflow scope using read-only GitHub App installation tokens. ADR-020 separately adds user linkage/access tokens for connection, discovery and current user-access verification; never substitute installation access when user authorization fails. Do not turn evidence collection into workflow mutation or artifact publication. Validate incoming source data and caller authenticity at the trust boundary using the agreed integration contract; do not assume an inbound event authorizes subsequent reads.
- Apply masking, anonymization, secret filtering and data minimization before evidence reaches the broker or downstream AI processing. Check failure paths and logs for sensitive-data exposure as well as the published payload. Preserve provenance and canonical context, including `correlationId`, through normalization.
- Do not infer persistent tables or a secret store from logical connector ownership. ADR-020 assigns linkage/credentials to Ingestion, but physical schema, custody, migrations and permissions require accepted definitions before credential persistence. Do not write downstream-owned data, register Pipeline objects/grants or introduce a separate privacy gateway. Check capture, normalization and publication together when changing behavior; use the agreed message and failure/re-delivery contracts rather than assuming exactly-once publication or choosing a deduplication scheme by inference.
- A request to implement a local increment authorizes its required local code, tooling and checks. Do not create cloud resources, permissions or secrets, or modify neighboring repositories as a side effect. Keep credentials and sensitive evidence out of committed files and reported output.
- If source authorization, webhook verification, event semantics or another required contract is unresolved, identify the specific pending decision and its impact. Continue independent work; do not invent integration behavior or block the whole service because an unrelated decision remains open.

## Verification and handoff

Use the applicable checks documented in the README. Add behavior checks with the first executable increment, including material failure cases for trust validation, sanitization, context preservation and publication. Use synthetic evidence and mocked integration boundaries for isolated tests; live GitHub or Azure checks need their own agreed scope and access.

For documentation-only edits, check affected links and source coherence; parse TOML when changing agent configuration. Do not claim a build or integration passed before it exists and has run. Keep the documentation that owns a changed behavior or command current in the same change. Report what changed, checks actually performed and remaining blockers. Keep handoffs in agent messages and durable accepted decisions in existing owning documents; do not create a document per increment. Do not publish branches, PRs or other changes without explicit user authorization.

## Task-based agent workflow

This repository authorizes the primary agent to delegate relevant work within the user's existing task authorization. For substantial work with ambiguous requirements, roadmap questions or consequential contract changes, use `service_analyst` for bounded research, the built-in `worker` for implementation and `ingestion_reviewer` for independent review. Use `explorer` for narrow code questions. Small, well-specified fixes can be implemented directly with proportionate review; do not run every role mechanically.

The primary agent remains responsible for scope, architecture consistency, integration, verification and completion. Reuse the analyst's evidence; reread sources when disputed, changed or insufficient. Carry forward applicable user approvals. Routine implementation choices do not require repeated confirmation. Only genuinely unresolved decisions block their dependent work; continue independent authorized work. Analysis/review does not add an approval layer or authorize publication, architecture changes or external writes.

Use this sequence when appropriate: bounded analysis → select specified and authorized work → worker implementation → independent review → fixes → primary-agent verification and report. Parallelize only independent tasks, with at most two open subagent threads excluding the primary. Assign workers explicit file ownership, scope, acceptance criteria and relevant paths; preserve others' changes and do not delegate integration conflicts away. Research/review roles do not edit or delegate.

Pass a compact feature brief, not the full research conversation:

- Goal, scope and exclusions; source links/paths, consulted revisions and relevant local changes.
- Consequential requirements with provenance and status: integrated, explicitly approved locally, proposed, assumed/inferred or unresolved. A local approval does not make the source integrated.
- Observable acceptance criteria and material failures; affected callers, contracts, persistence, configuration and dependencies.
- Open decisions with the exact question, impact, options/recommendation and documented approval authority (or its absence); ordered work ready now versus awaiting a decision/contract.

Workers implement the smallest complete authorized change, meaningful checks and owning documentation; return changed files, exact verification results, deviations and blockers. Escalate conflicting requirements without inventing policy. Reviewers receive the same brief but independently inspect connected paths and source assumptions, assess acceptance-criteria coverage and failure-test effectiveness, and distinguish simulated from real integration. Their findings supplement primary-agent verification and human review.

Keep handoffs in agent messages. Persist durable accepted decisions in existing owning documents; no document per increment. On the first suitable feature, assess repeated research, unnecessary clarification loops and requirement-related rework before adopting this pilot across services. Model/effort defaults and configuration discovery are documented in the [optional Codex setup](README.md#optional-codex-setup); adjust them to demonstrated task complexity rather than using maximum effort by default.
